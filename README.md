# PhysicalChess

턴 없이 실시간으로 겨루는 1:1 체스 게임. Google Play 배포가 목표다.

## 컨셉

- **극한의 피지컬 싸움**: 반응속도와 순간 판단력으로 승부가 갈린다. 승부욕을 최대치로 끌어올리는 것이 목표다.
- **턴이 없다**: 두 플레이어가 동시에, 원할 때 말을 움직인다.
- **말은 스킬샷처럼 날아간다**: 예를 들어 비숍은 대각선을 따라 시간을 들여 이동한다. "말을 누르고 칸을 누르는" 방식은 쓰지 않는다.
- **이동 중 방향 전환**: 날아가는 말을 잡아서 적절한 타이밍에 다른 곳을 터치하면 도중에 방향을 바꿀 수 있다.

## 정해진 것

| 항목 | 결정 |
|---|---|
| 인원 | 1:1 온라인 대전 |
| 플랫폼 | 모바일(폰, 태블릿), Android 우선 |
| 판정 | 서버가 모든 판정을 확정한다 |
| 랭크 게임 | 단판승, 끝난 뒤 리매치 신청 가능 |
| 프로 리그(생긴다면) | 3판 2선승 또는 5판 3선승 |
| 한 판 최대 시간 | 3분 (시제품에서 조정할 수 있게 설정값으로 둔다) |

## 아직 정하지 않은 것

- **방향 전환 지점**: 아무 위치에서나 꺾을 수 있는지, 칸 중앙을 지날 때만인지
- **전환 후 이동 규칙**: 꺾은 뒤에도 그 말의 원래 이동 규칙(비숍은 대각선)을 따르는지
- **충돌 결과**: 움직이는 말끼리 만났을 때 어떻게 되는지
- **이동 제한**: 쿨다운을 두는지, 둔다면 말마다인지 전체인지
- **동시 조작**: 여러 손가락으로 여러 말을 한꺼번에 움직일 수 있는지
- **승리 조건**: 킹을 잡으면 이기는지
- **시간 초과 시 승패**: 남은 말의 가치로 정할지, 연장전으로 갈지
- **리매치 제한**: 연속 횟수 제한과 랭크 점수 반영 방식
- **화면 표현**: 위에서 내려다보는 고정 시점이 유력하다
- **개발 도구**: 컨셉이 확정되면 정한다. 지금 저장소의 Unreal Engine 5.4.4 템플릿은 확정이 아니다

# 개발 방법론 (AI 협업)

(2026-11-22 결정)

### 0. 한 장 요약
- 역할: 사람 = 승인 버튼 · 결과 확인 · 방향 판단 · push / AI = 계획 · 구현 · 쪼갠 커밋 · 병합 · 빌드 · 앱 켜기 · 빠른 점검
- 흐름: 계획(메시지로 확인) → 워크트리에서 구현 → 단위별 커밋 → 확인 지점에서 멈추고 승인 버튼 → 승인되면 AI 가 본체에 병합 → 빌드 → 앱 켜기 → "여기를 보세요" → 사람이 직접 확인·방향 판단 → 다음 구간
- 결과 확인(화면으로 동작 보기)은 사람이 직접 한다 — AI 가 하면 느리다. AI 는 컴파일·로그처럼 빨리 끝나는 점검만
- 확인 지점은 넉넉히, 짧고 잦게
- 글은 짧게·목록으로·사실만, 이유는 한 줄. 문서에 설명문·코드 스니펫 쓰지 않음
- 함정은 반드시 글로 남긴다 (폴더 README 함정 절, 코드의 계약 주석)
- AI 가 못 만지는 것은 도구를 만들어 손을 넓힌다. 그래도 못 하는 건 조용히 넘기지 않고 "X 가 안 된다" 고 말한다

### 1. 규칙 문서
- 공통 규칙은 한 곳에만 둔다(이 절). 에이전트별 파일(CLAUDE.md·AGENTS.md)은 "이 절을 먼저 읽을 것" + 그 에이전트에만 뜻 있는 것만
- 규칙에는 결정한 날짜를 붙인다 — "(YYYY-MM-DD 결정)". 나중에 왜·언제부터인지 추적
- 규칙을 바꾸면 같은 규칙을 말하는 다른 파일(도구 README 등)도 같은 커밋에서 고친다 — 옛 문장이 남으면 에이전트가 옛 규칙대로 움직인다
- 규칙 파일은 꼭 push 한다 — 여러 PC 에서 일하면 push 안 된 PC 의 에이전트는 옛 규칙대로 움직인다
- 규칙에 PC 별 절대 경로를 박지 않는다 ("본체 = main 체크아웃" 처럼 쓴다)
- 같은 내용을 두 곳에 쓰지 않는다 — 한쪽만 고쳐져 어긋난다
- README 앞부분 = 프로젝트 전체 메모: 설계 의도, "새 X 추가할 때 개발 순서", 기억할 설정

### 2. 폴더 README
- 주요 폴더마다 README.md 를 둔다. 그 폴더의 파일을 고치기 전에 읽는다 (대상 폴더: Source/PhysicalChess — 폴더가 생기면 추가)
- 내용은 "뭐가 있고 / 어디서 쓰이나 / 함정" 세 덩어리. 20줄 이내. 코드 설명·함수 시그니처 금지
- 폴더 내용이 바뀌면(파일 추가·삭제·역할 변경) 같은 커밋에 그 README 도 고친다
- 함정 줄 끝에 `(grep: 키워드)` 를 붙이고 코드 주석에도 같은 키워드를 박아 한 번에 찾게 한다
- 작업 종류별로 "먼저 읽을 README" 를 이 절에 건다 (예: "모델 파일을 만들기 전에 <폴더>/README.md")
- 배포물에 같이 실리는 README 에는 외부 전용 정보(계정·비번·내부 주소) 금지

### 3. 계약 주석 — 건드리면 깨지는 곳
- 리팩터링하면 깨지는 구간은 코드에 `[<이름> 계약]` 주석을 달고, 아래 「주의사항」에 "수정 전 <파일>의 [<이름> 계약] 주석 필독" 으로 건다
- 외부(다른 저장소·배포본·스크립트·에셋)에서 부르는 공개 API 는 삭제·개명 금지. "저장소 grep 으로 호출부 없음이 나와도 믿지 말 것"

### 4. 코드 규칙
- 파일 인코딩·줄바꿈: <예: UTF-8(BOM 없음) + CRLF>
- 주석·로그 문구는 한글, 식별자(클래스·함수·변수 이름)는 영문
- 로그는 `[태그]` 로 시작 — 로그 창에서 태그로 찾는다
- 새 기능의 큰 로직은 <중심 클래스>에 쌓지 말고 컴포넌트·별도 클래스로 분리
- 데이터 파일 폴더를 새로 만들면 패키징·배포 등록도 같이 — 빠뜨려도 개발 중엔 멀쩡하고 배포본에서만 조용히 사라진다

### 5. 계획
- 기능 단위 작업은 구현 전에 계획을 메시지로 확인받는다. 문서는 만들지 않는다
- 메시지에는 셋만. 방법·순서·위험은 적지 말고 알아서 한다
  - 완성 모습: 코드를 모르는 사람이 읽는 시나리오 — 사용자가 뭘 하면 뭐가 보이나, 지금과 뭐가 다른가. 개발 용어·클래스 이름 금지. 겉으로 안 바뀌면 "겉으로 달라지는 것 없음 — <내부 변화>" 한 줄
  - 중간 확인 지점: 어디서 멈추고 뭘 보면 되나
  - 손대는 파일: 수정 / 새로 만듦
- 한 세션에 안 끝날 것 같은 작업이면 "계획을 Docs/Plans/ 문서로 남길까요?" 를 한 번 묻고, 그러자고 할 때만 아래 템플릿으로 만든다
- Docs/Plans/ 에는 진행 중인 계획만 둔다. 끝난 계획서는 지우되, 남길 이유·함정은 그 코드 주석이나 폴더 README 로 먼저 옮긴다
  - 지운 계획서 찾기: `git log --diff-filter=D --name-only -- Docs/Plans` → `git show <커밋>^:<경로>`
  - 미병합 브랜치가 고친 계획서를 지우면 그 브랜치를 병합할 때 충돌한다 — 브랜치 먼저 정리
- 큰 묶음은 `<기능>_<n>_<부제>.md` 로 번호를 잇는다
- 계획서 템플릿(Docs/Plans/_template.md):
  ```
  # <기능 이름>
  ## 완성 모습
  - 코드 모르는 사람용. 사용자가 뭘 하면 → 뭐가 보이나, 지금과 다른 점. 10줄 이내
  ## 확인 지점
  1. 멈추는 곳마다: 그때까지 된 것 → 사용자가 볼 것 (또는 직접 할 것)
  ## 손대는 파일
  - 수정: 경로
  - 새로 만듦: 경로
  ## 결과
  - (구현 뒤) 커밋, 계획과 달라진 점
  ```

### 6. 본체 폴더 / 워크트리
- 본체(main 체크아웃)는 사용자의 작업·실행 공간이며 항상 main 으로 유지한다
- AI 는 별도 worktree 의 작업 브랜치에서만 수정·커밋한다. 새 브랜치를 만들 때도 본체에서 체크아웃·브랜치 전환을 하지 않는다
- 작업 시작 전 본체의 현재 브랜치·미커밋 변경, 작업할 worktree 의 경로·분기 기준을 확인한다. 본체가 main 이 아니면 임의로 전환하지 말고 알린다
- 본체에서 Git 상태 조회는 되지만 스테이징·커밋·병합은 하지 않는다. 예외는 「8. 확인 지점 병합」의 승인된 병합 하나뿐
- 본체의 사용자 변경을 임의로 stash·reset·clean 하거나 작업 커밋에 섞지 않는다
- 워크트리와 본체를 정션·심링크로 잇지 않는다 (워크트리 삭제 때 본체까지 지워질 수 있다)
- (Claude 앱) 시작 바에 표시된 브랜치가 워크트리 분기 기준이므로 시작 전 확인. 워크트리 브랜치 이름은 첫 메시지에서 자동 생성되므로 첫 메시지를 작업 내용으로 시작

### 7. 커밋
- 사람이 읽기 쉬운 단위로 쪼개서, 요청을 기다리지 말고 알아서 커밋한다. 커밋은 확정이 아니라 저장점(검토 후 되감으면 됨)
- push 는 하지 않는다(사람이 한다). 병합은 사람이 직접 하거나, AI 가 확인 지점에서 승인을 받아서만 한다. 승인 없이 병합 금지
- diff 를 채팅에 길게 붙이지 않는다 (사람이 IDE 에서 커밋별로 본다)
- 메시지
  - 제목: `<영역 또는 파일>: <바뀐 사실>`
  - 본문: 파일별로 묶어 바뀐 사실만, 이유는 항목마다 한 줄까지
  - 요청 근거: `사용자 YYYY-MM-DD "…"`
  - 점검 한 줄: 예 "단일 파일 컴파일 3개 통과"
  - 일부러 커밋하지 않은 것도 적는다: 예 "시험 파일은 규칙대로 커밋 안 함"
- 커밋 금지 목록: `.claude/settings.local.json`, 시험용 파일

### 8. 확인 지점 병합 (승인 버튼 → 테스트할 상태 만들기)
- 확인 지점까지 커밋하고 멈춘다. "뭘 보면 되나" 한 줄과 함께 "확인을 누르면 병합해서 테스트할 상태로 만들어 두겠습니다" 버튼을 띄우고 기다린다. 승인은 그 한 번에만 유효
- 승인되면 본체에서 `git merge --no-ff <작업 브랜치>` → (코드가 바뀌었으면) 빌드 → 앱 켜기 → "여기를 보세요". 결과 확인은 사용자가 직접
- 멈추고 묻는 경우
  - 본체가 main 이 아님
  - 본체의 미커밋 변경이 병합할 파일과 겹침 (안 겹치는 미커밋 변경은 그대로 둔다)
  - 앱에 저장 안 된 것이 있음
  - 충돌 — `git merge --abort` 뒤 알린다. 바이너리 파일은 한쪽을 임의로 고르지 않는다
- 한 번에 한 세션만. 다른 세션 브랜치를 같이 올리는 건 사용자가 시킬 때만
- 마음에 안 든다는 답이 오면 되돌리지 말고 워크트리에서 그 위에 고쳐 다음 확인 지점에 다시 올린다. 병합 커밋 되돌리기는 통째로 버릴 때만 (되돌린 브랜치는 다시 병합해도 예전 커밋이 안 돌아온다)
- 승인 버튼이 없는 에이전트(Codex 등)는 병합하지 않고 "사용자가 직접 병합" 으로 둔다

### 9. 병합 잠금 (세션을 여러 개 동시에 돌릴 때) (이 프로젝트 해당 없음 — 스크립트 아직 없음)
- 왜: 병합과 빌드 사이에 앱을 끄는 틈(수십 초)에 다른 세션이 병합하면 두 세션의 변경이 한 빌드에 섞인다. 빌드 프로세스만 봐서는 이 틈을 못 막는다
- 잠금 스크립트 `Scripts/Build/merge_lock.py` (워크트리에서 실행, 작업 브랜치 이름이 잠금 주인으로 적힘)
  - 잠금 파일은 본체 `.git/claude-merge.lock` — 모든 워크트리가 같이 보고 커밋에 안 섞인다
  - 병합 직전 `acquire`, 앱을 켠 뒤(빌드가 없으면 병합 직후)와 중간에 멈출 때 `release`, 상태만 볼 땐 `status`
- acquire 종료 코드
  - 0 잡음 → 진행
  - 1 다른 세션이 쓰는 중이거나, 잠금은 없지만 본체 빌드(<빌드 프로세스 이름>)가 도는 중 → 병합하지 말고 "지금 「○○」 세션이 병합·빌드 중이라 보류했습니다. 끝나면 눌러 주세요" 버튼으로 멈춘다. 끝나도 알아서 이어가지 않는다(사용자가 그 세션 결과를 테스트 중일 수 있음)
  - 2 남은 잠금으로 보임(30분 넘었고 빌드 없음) → 사용자에게 풀지 묻고, 풀라고 하면 `release --force` 뒤 다시 `acquire`
- 빌드가 실패하면 잠금을 쥔 채 워크트리에서 고쳐 다시 병합·빌드한다. 이번 차례에 못 고치면 풀면서 "main 이 지금 빌드가 안 된다" 고 알린다
- 문서·Scripts/ 만 바뀐 병합은 잠금이 필요 없다
- 한계: 사용자가 GUI 로 직접 하는 병합과, 이 규칙이 들어오기 전에 만든 워크트리 세션은 잠금을 모른다

### 10. 빌드 · 앱 켜기
- 병합 뒤 빌드·앱 켜기는 AI 가 한다. 절차는 스크립트와 Scripts/Build/README.md 로 고정한다
- 순서
  1. 앱이 켜져 있으면 저장 안 된 것을 확인한다(<확인 방법>). 있으면 사용자에게 묻는다. 없으면 열린 편집 창을 닫고 정상 종료(<종료 방법>)
  2. 빌드(<빌드 명령>) — 백그라운드로 돌리고 로그의 오류 줄·소요 시간만 본다
  3. 앱 켜기(<실행 명령>) — 떴는지만 확인
  4. 보고: "빌드 OK/실패(오류 줄) → 앱 켜짐 → 여기를 보세요"
- AI 가 빌드하는 동안 IDE 에서 같은 타깃을 빌드하지 않는다 (산출물 충돌)
- 실행 중 앱에 임시 객체를 만드는 스크립트는 반드시 try/finally 로 지운다 (남으면 사용자가 저장할 때 같이 들어간다)
- 사용자가 화면 확인을 시키면 컴퓨터 사용으로(스크린샷·클릭). 미리 보기류는 숫자가 아니라 화면으로 확인
- 빌드·실행에서 겪은 함정은 날짜와 함께 Scripts/Build/README.md 함정 절에

### 11. 확인 분담
- 결과 확인(화면으로 동작을 보는 것)은 사용자가 직접 한다 — 에이전트가 하면 느리다. 화면 확인은 사용자가 시킬 때만
- 에이전트는 컴파일·빌드 성공, 로그 오류 없음, 덤프 대조처럼 빨리 끝나는 확인만 하고 바로 볼 수 있는 상태로 넘긴다
- 넘길 때 체크리스트를 통째로 주지 않는다. "뭘 보면 되나" 를 짧게 번호로. 방향이 결정되는 부분(디자인·기획·기능)은 따로 묻는다
- 중간 확인 지점은 넉넉히: 기능이 다 끝날 때까지 기다리지 말고, 화면에서 볼 수 있는 단위가 될 때마다 멈춰 사용자가 결과를 보게 한다. 멈출 때마다 "뭘 보면 되나" 한 줄
- 기능 하나가 끝나면 다음 일을 제안하기 전에 "원하던 모양인가" 를 볼 자리를 만든다(5~10분, 짧고 잦게): 바로 볼 수 있게 세팅한 상태 + "여기를 보세요" 1~3줄 + 방향을 묻는 질문 2~3개
- 작업이 길면 논리 단위마다 끊어서 멈춘다. 한 번에 다 하고 끝내지 않는다

### 12. AI 가 못 만지는 것 다루기
- AI 가 직접 못 읽는 포맷(바이너리·GUI 전용 데이터)은 두 도구를 만든다
  - 읽기 도구: 앱 없이 디스크 저장본을 텍스트로 덤프
  - 쓰기 도구: 실행 중 앱 안에서 도는 작은 API — 결과가 화면에 바로 보이고 Undo 되게, 실패하면 저장 안 되게. 설정 파일 없이 AI 가 그 자리에서 짧은 스크립트를 써서 보낸다
- 흐름: 덤프 → 스크립트 → 실행 → 저장 → 다시 덤프해 대조 → 파일 단위 커밋
- 이름은 덤프 출력 그대로 쓴다. 덤프 전에 대상이 저장돼 있어야 이름이 맞는다
- 도구가 못 하는 것은 체크리스트로 조용히 넘기지 말고 "도구에 X 가 없다" 고 알린다 → 도구를 늘릴지 사용자가 판단
- 도구 README 에 함수 목록·예시를 두고 이 절에 "먼저 읽을 것" 으로 건다
- 시험용 파일은 커밋하지 않는다

### 13. 소통
- 요청이 애매하거나 말이 어색하면 추측으로 진행하지 말고 먼저 되묻는다. 단, 사소한 건 기본값으로 진행하고 그렇게 했다고 한 줄만
- 사용자가 틀린 전제(함수 역할·이름·구조)로 말하면 따라가지 말고 바로 지적한다
- 사용자가 쓴 용어가 코드 이름과 다르면 어느 쪽을 말하는지 확인한다

### 14. 세션 정리 (Claude 앱)
- 세션 삭제 요청이 오면 먼저 확인: 워크트리에 저장 안 된 변경, `git log main..HEAD` 가 비었는지. 결과를 표로
- main 에 없는 커밋이 있으면 병합을 기본으로 안내하지 말고 묻는다: 합칠지 / 브랜치만 남길지 / 버릴지 (커밋 목록과 빌드 필요 여부를 같이)
- 브랜치·워크트리·세션 기록·임시 파일은 손대지 않는다. 앱에서 세션을 지우면 같이 지워진다 (`worktree remove`, `branch -d` 직접 실행 금지)
- 현재 세션은 AI 가 못 지운다 → "앱에서 세션을 삭제하면 끝" 이라고 안내
- 세션과 별개라 따로 처리: 계획 파일(`~/.claude/plans/*.md`, 같은 내용이 Docs/Plans/ 에 있으면 물어보고 삭제), 메모리를 최종 상태(병합 여부·남은 일)로 고침
- 메모리는 PC 마다 따로다 — 중요한 결정은 메모리가 아니라 이 절에 적는다
- 삭제 뒤 `.claude/worktrees/` 에 빈 폴더가 남을 수 있고, 다른 세션에서 "미등록 빈 폴더 지워줘" 로 정리하면 된다고 한 번 안내
